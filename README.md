# Harness — 이식용 에이전트 하네스

AI 코딩 에이전트가 **"검사를 안 했다"와 "검사를 통과했다"를 같은 침묵으로
내보내지 못하게** 하는, 다른 프로젝트에 붙이는 하네스.

Claude Code 에서도 돌고, git 훅으로 **어느 에이전트에서도** 돈다.

---

## 1. 무슨 문제를 푸는가

에이전트에게 일을 시키면 이런 대답이 돌아온다.

> 수정했습니다. 타입 검사도 통과했습니다.

문제는 이 문장이 **두 가지 완전히 다른 상황에서 똑같이 나온다**는 것이다.

| 실제로 일어난 일 | 에이전트가 하는 말 |
|---|---|
| 타입 검사를 돌렸고, 오류가 없었다 | "통과했습니다" |
| 타입 검사기가 설치돼 있지 않아 **아무것도 안 돌았다** | "통과했습니다" |

둘째가 위험한 이유는 틀렸기 때문이 아니라, **첫째와 구별되지 않기 때문**이다.
사람은 검사가 돌았다고 믿고 넘어간다. 그리고 그 믿음은 몇 주 뒤에 깨진다.

이건 에이전트의 정직성 문제가 아니라 **출구가 하나뿐인 구조**의 문제다.
"검사 없음"과 "검사 통과"가 같은 종료 코드 `0` 으로 나가면, 아무리 성실해도
둘을 나눠 말할 방법이 없다.

**이 하네스가 하는 일은 그 출구를 나누는 것이다.**

### 왜 "조용한 실패"가 특별히 나쁜가

시끄럽게 실패하는 도구는 고쳐진다. 조용히 실패하는 도구는 **고쳐지지 않는 채로
신뢰를 얻는다.** 그리고 그 신뢰가 쌓일수록 피해가 커진다.

이 저장소를 만들면서 실제로 겪은 것들이다 —

- 훅 설정에 **없는 이벤트 이름**을 썼다. 등록됐고, 오류도 없었고, 영원히 안 돌았다
- 훅 스크립트를 `.bat` 으로 뒀다. git 은 `.bat` 훅을 **말없이 무시한다**
- 문서에 적힌 훅 경로가 **지워진 파일**을 가리키고 있었다. 그대로 등록했다면
  훅은 있고, 오류도 없고, 아무것도 안 했을 것이다
- 게이트가 한글 경로를 **못 알아봤다**. git 이 비ASCII 경로를 따옴표로 감싸는데
  정규식이 그걸 몰랐다. 한글 파일만 검사에서 조용히 빠졌다

전부 "경고 하나 없이 잘 돌아가는 것처럼 보이는" 실패다.
**하네스가 막으려는 건 버그가 아니라 이 침묵이다.**

## 2. 핵심 아이디어 — 판정은 네 가지다

보통 검사 도구는 결과를 둘로 말한다. 통과 / 실패.
이 하네스는 **넷**으로 말한다.

| 판정 | 뜻 | 예 |
|---|---|---|
| `skip` | **내 소관이 아니다** | 타입 검사기가 `.md` 파일 편집을 봤다 |
| `pass` | 검사했고, 문제없다 | 타입 검사를 돌렸고 오류가 없다 |
| `block` | 검사했고, 문제가 있다 | 타입 오류가 있다 |
| `cannot` | **소관인데 판정하지 못했다** | `.ts` 인데 타입 검사기가 없다 |

`cannot` 이 이 하네스의 전부라고 해도 된다.

> **`skip` 은 "내 사건이 아니다" 한 가지 뜻으로만 쓴다.
> 소관인데 판정에 실패했으면 전부 `cannot` 이고, 그건 절대 `pass` 로 접히지 않는다.**

이게 **제1원칙**이다. 게이트가 죽는 방식은 여러 가지다 — 입력이 깨짐, 실행
파일이 없음, 시간 초과로 강제 종료됨, 게이트 자신의 버그. 그 전부가 조용한
종료로 나가면 게이트는 **있어도 없는 것과 같고, 있다고 믿기 때문에 더 나쁘다.**

### 판정과 전달을 분리한다

환경마다 "막는다"를 표현하는 방법이 다르다.

| 환경 | 통과 | 막음 |
|---|---|---|
| Claude Code 훅 | `0` | `2` (`1` 은 **경고로 지나간다**) |
| git 훅 | `0` | `1` |
| 명령줄 도구 | `0` | `1` · 판정 불가 `2` |

숫자가 다 다르다. 그래서 판정하는 코드가 종료 코드를 직접 다루면, 환경을
옮길 때마다 `cannot` 이 슬그머니 `pass` 로 접힐 자리가 생긴다.

그래서 **판정하는 곳과 내보내는 곳을 갈라 놨다.**
판정 코드는 네 값 중 하나만 돌려주고, 숫자로 옮기는 일은 어댑터만 안다.
원칙이 **코드 구조로 강제된다** — 지키자는 약속이 아니라.

### 제2원칙 — 거짓 차단을 피한다

정반대 방향의 위험도 있다. 멀쩡한 작업을 자꾸 막으면 **사람이 게이트를 꺼 버린다.**
그리고 꺼진 게이트는 없는 것보다 나쁘다. 있다고 믿기 때문이다.

그래서 검사를 넣을 때마다 두 번 묻는다.

1. 이게 **정상적인 작업**에서도 걸리나?
2. 걸린다면 — **막을 것인가, 알리기만 할 것인가?**

실제로 그렇게 갈려 있다. 상태 문서를 같이 안 고친 커밋은 **막고**(예외가 거의
없다), 테스트를 같이 안 고친 커밋은 **알리기만 한다**(주석 수정이나 리팩터링에
흔하다). 두 원칙은 서로를 당긴다 — 한쪽만 밀면 다른 쪽이 무너진다.

## 3. 게이트는 두 계층이다

같은 판정을 **두 군데**에서 건다. 중복이 아니라 **상보**다.

```
   에이전트가 파일을 고친다
        │
        ├─ [도구 계층]  Claude Code 훅 — 편집 직후 · 명령 직전
        │               우회 불가. 대신 Claude Code 에서만 산다
        ↓
   에이전트가 커밋한다
        │
        └─ [커밋 계층]  git 훅 — pre-commit · commit-msg
                        어느 에이전트든 산다. 대신 --no-verify 로 뚫린다
```

| | 도구 계층 | 커밋 계층 |
|---|---|---|
| 언제 | 편집·명령의 **직전/직후** | 커밋할 때 |
| 어디서 | Claude Code 안에서만 | **Codex · Gemini · Cursor · 손 커밋까지** |
| 우회 | **안 된다** | `--no-verify` 로 뚫린다 |
| 설치 | 사용자 전역에 한 번 | 저장소마다 |

한쪽만 있으면 각각 이렇게 샌다 —

- **도구 계층만** → 다른 에이전트로 갈아타는 순간 게이트가 하나도 없다
- **커밋 계층만** → 편집 직후 피드백이 없고, `--no-verify` 한 줄이면 끝난다

그리고 이 결손은 **눈에 잘 안 띈다.** 게이트 하나하나는 "한 계층에만 살아도"
살아 있는 것으로 보이기 때문이다. 그래서 생존 판정 도구가 **계층이 통째로
비어 있는 경우를 따로 말한다.** 막지는 않는다 — Claude Code 에서만 쓰기로
정한 사람도 있으니까(제2원칙).

## 4. 게이트는 "단계"를 모른다 — 경로로 켜진다

흔한 설계는 "지금은 기획 단계", "지금은 구현 단계" 를 선언하게 하는 것이다.
**그렇게 하지 않았다.** 이유가 둘이다.

1. **선언은 낡는다.** 단계를 바꿔 적는 걸 잊으면 게이트가 엉뚱하게 켜진다
2. **애자일에서 기획·구현·QA·문서화는 단계가 아니다.** 매 반복에 다시 온다.
   단계로 만들면 그건 애자일이 아니라 워터폴이다

대신 게이트는 **커밋이 무엇을 건드렸는가**만 본다.

| 건드린 것 | 켜지는 게이트 |
|---|---|
| 결정 문서 | 미결 목록을 같이 정리했나 (닫은 것을 두 곳에 남기지 않았나) |
| 소스 코드 | 요구 문서와 구조 문서가 채워져 있나 · 컴파일/타입이 맞나 |
| 마이그레이션 | 이미 적용된 파일을 고치려는 것 아닌가 |
| 무엇이든 | 상태 문서를 같이 고쳤나 · 문서가 크기 한도 안인가 |

**선언할 게 없으니 낡을 것도 없다.**

## 5. 문서 — 여섯 개, 각각 하나의 질문

에이전트가 세션마다 읽는 문서다. 각각 **하나의 질문에만** 답한다.
답이 겹치면 두 벌이 되고, 두 벌은 반드시 서로 어긋난다.

| 문서 | 답하는 질문 |
|---|---|
| `PRD.md` | 무엇을, 왜, 누구에게 만드나 — 그리고 무엇을 기준으로 고르나 |
| `ARCHITECTURE.md` | 무엇이 어디 있고 무엇과 이어지나 (C4 L1·L2) |
| `STATUS.md` | 지금 무엇이 되어 있고, 다음이 무엇인가 |
| `RUNBOOK.md` | 명령을 어떻게 돌리고, 그 명령이 **어떻게 실패하나** |
| `AGENTS.md` | 이 저장소에서 일하는 규칙 (**진본**) |
| `decisions/` | 왜 그렇게 정했나 · 아직 안 정한 것 |

### 규칙 1 — 세션마다 읽는 문서는 3KB 한도다

세션마다 읽히는 문서는 **컨텍스트를 먹는다.** 먹은 만큼 정작 일할 자리가 준다.
그래서 한도는 세션 시작에 읽는 셋(`AGENTS`·`STATUS`·`RUNBOOK`)과, 한도 자체가
신호인 미결 목록에 걸린다. `PRD`·`ARCHITECTURE` 는 필요할 때 읽고 프로젝트와
함께 **자라야** 하므로 걸지 않는다 — 걸면 기능을 넣으려고 품질 목표를 지우게 된다.

중요한 건 한도 자체가 아니라 **넘쳤을 때 무엇을 하느냐**다.

> **늘리지 말고 내려보낸다.**

- 지나간 사건은 상태가 아니다 → 지운다 (커밋 메시지에 남는다)
- 조건부로만 필요한 규칙 → 조건부 로드 파일로 내린다
- 이유가 긴 것 → 결정 문서로 옮긴다
- 밀려난 지뢰 → 보관 파일로 옮긴다. **지우지 않는다** — 죽었다는 판단이 틀릴 수 있다

**배출구가 있을 때만 한도가 한도다.** 배출구 없는 한도는 벽이고,
벽에 부딪히면 사람은 **시행 중인 규칙을 지워서** 자리를 만든다.
그건 파일이 큰 것보다 나쁘다.

### 규칙 2 — 도구가 말할 수 있는 것은 적지 않는다

문서에 **관측값**(도구가 매번 다시 세는 수 — 테스트 건수, 결정 개수, 파일
크기)을 적지 않는다. 값 대신 **부르는 법**을 적는다.

```
- 되는 것 — 131건 회귀로 검증됨
+ 되는 것 — 변조 회귀로 검증됨 (`verify` 가 센다)
```

이유는 낡기 때문만이 아니라 **낡은 게 안 보이기 때문**이다.
`43건` 은 `131건` 과 똑같이 생겼다. 오류도 diff 도 없다 —
이 하네스가 없애려는 바로 그 침묵이다.

가르는 한 줄:

> **문서를 안 고쳐도 이 값이 틀려질 수 있나?**

| | 예 | 적나 |
|---|---|---|
| **결정값** — 사람이 문서를 고쳐야 바뀐다 | 3KB 한도 · 10개 기준 | 적는다 |
| **기록된 과거** — 날짜가 박힌 측정 | "이식 직후 81바이트 넘었다" | 적는다 |
| **관측값** — 도구가 매번 다시 센다 | 건수 · 개수 · 크기 | **안 적는다** |

### 규칙 3 — 규칙은 한 벌만 둔다

`AGENTS.md` 가 진본이고, `CLAUDE.md`·`GEMINI.md`·`.cursor/rules/` 는 전부
그걸 **가리키는 포인터**다. 복사본을 두면 한쪽만 고쳐지고, 그러면 어느 쪽이
맞는지 아무도 모른다.

## 6. 결정을 다루는 방식 — 세 구역

생각은 확정되기 전에 떠돈다. 그 떠도는 상태를 **어디에 둘지**가 정해져 있다.

```
  docs/                decisions/OPEN.md          decisions/D<n>
  탐색 — 자유롭게      "지금 고르는 중"           닫힌 결정 — 영구
       ──────────→            ──────────→
                      (닫으면 위로 올리고
                       OPEN 에서는 지운다)
```

- **두 곳에 두지 않는다.** 닫힌 것이 미결 목록에도 남아 있으면 훑는 비용만
  오르고, 훑는 비용이 오르면 **아무도 안 연다**
- **결정 문서에는 근거와 "뒤집힐 조건"을 반드시 적는다.** 뒤집힐 조건이 없는
  결정은 신앙이지 결정이 아니다
- **원본은 고치지 않는다.** 생각이 바뀌면 새 번호로 "D\<n\>을 고친다" 로 잇는다.
  그래야 왜 바뀌었는지가 남는다
- 미결 목록에도 **3KB 한도**가 걸린다. **그게 셈이다** — 표가 넘치면 넓히기만
  하고 고르지 않고 있다는 뜻이다. 넘치면 늘리지 말고 **닫아라**

### 관측인가 결정인가

모든 걸 결정 문서로 만들면 결정 로그가 **도구 사고 속도로** 자란다.

| | 성격 | 어디로 |
|---|---|---|
| **관측** | 선택지가 없다. 그냥 그렇다 | 런북의 지뢰표 한 줄 |
| **결정** | 대안·근거·뒤집힐 조건이 있다 | 결정 문서 |

**같은 도구 실패가 두 번째면 관측이 아니라 결정이다.**

## 7. 반복 — 단계가 아니라 바퀴

```
        ┌──────────── 기획 ────────────┐
        │                              │
        ↓                              │
      구현 ──────→ QA ──────→ 문서화 ──┘
                                (회고)
```

넷은 **순서**가 아니라 **한 바퀴**다. 구현 중에 생긴 의문이 기획으로 돌아가는
화살표가 있어야 원이 닫힌다 — 그 화살표가 **미결 목록**이다.

반복의 경계는 가볍다. 상태 문서에 **시작일과 목표 한 줄**이 전부다.

- 목표는 **끝났을 때 판정할 수 있는 말**로 쓴다.
  "인증 개선" 은 판정이 안 된다. "로그인이 외부 인증으로 된다" 는 된다
- 끝나면 회고 스킬이 닫고 다음 반복을 연다.
  **회고는 새 파일을 만들지 않는다** — 산출물은 이미 있는 네 곳으로 흩어지고,
  서술은 **회고 커밋 메시지**에 남는다. 그래서 파일도 예산도 늘지 않는다
- 목표를 슬쩍 줄여서 "됐다" 로 만들지 않는다. 그건 회고가 아니라 합리화다

### 기능이 끝났다는 판정도 명령이다

기능마다 **완료 판정을 실행 가능한 명령 하나**로 적어 둔다.

> "로그인이 동작한다" 는 에이전트가 **말로 통과시킬 수 있다.**
> 명령은 종료 코드가 말한다.

제1원칙의 기능판이다. 그리고 규칙은 하나 — **기능이 끝났다고 말하기 전에
그 명령을 돌린다. 안 돌렸으면 끝난 게 아니다.**

이 규칙은 문서에만 두지 않는다. 판정은 `done.mjs F<n>` 으로 돌리고, 그것이
**어느 코드에 대해 돌았는지**(워킹트리 해시)를 남긴다. 소스를 바꾼 턴이 그 기록
없이 끝나려 하면 Stop 훅이 **한 번** 막는다.

- **결과가 아니라 돌았는지만 본다.** 턴은 기능이 끝날 때만 끝나지 않는다 — 중간
  보고에서 판정이 실패하는 건 정상이다. 결과까지 요구하면 모든 중간 턴이 막힌다
- **한 번만 막는다.** 두 번 막으면 턴이 끝나지 않는다
- **세지 않는다.** 남는 것은 세션 시작 트리와 판정 기록, 둘 다 내용 해시다

---

## 8. 붙이는 법

```bash
# 한 번만 — 도구 계층 (사용자 전역)
node <하네스>/adapters/claude-code/install.mjs          # 계획만 보여 준다
node <하네스>/adapters/claude-code/install.mjs --apply  # 승인한 뒤에 쓴다

# 프로젝트마다
git init <프로젝트>
node <하네스>/scripts/apply-template.mjs <프로젝트>
node <하네스>/adapters/git/install.mjs   <프로젝트>
node <하네스>/scripts/gates-report.mjs   <프로젝트>   # ← 통과해야 끝이다
```

**빈 폴더에서 새로 시작하는 것이면 `/harness-init` 스킬을 쓴다.**
위를 부르고, 그 세션에서 사람에게 묻고, 문서를 채우고, 완료 판정까지 본다.

역할이 갈려 있다 — **스크립트가 놓고 스킬이 채운다.**

| | 누가 | 왜 |
|---|---|---|
| **무엇이 있어야 하는가** | 스크립트 | 목록이 코드에 있다. 빠뜨리면 회귀가 잡는다 |
| **무엇을 적어야 하는가** | 에이전트 | 판단이 필요하다. 대신 **산출물에 판정을 건다** |

스킬이 파일을 직접 놓지 않는 이유는 간단하다 — **빠뜨려도 조용하기 때문**이다.

## 9. 세 개의 명령

```bash
node scripts/verify.mjs          # 판정이 맞나  (변조 회귀)
node scripts/gates-report.mjs    # 그 판정이 걸려 있나
node scripts/budget.mjs          # 문서가 한도 안인가
```

앞의 둘은 **하나만 보면 반쪽이다.**

- `verify` 의 "전부 통과" 는 **"전부 돌았다" 가 아니다.**
  도구가 없어 못 돌린 사례를 따로 찍는다 — 조용히 빼면 그게 통과로 읽힌다
- `gates-report` 의 "등록됨" 은 **"발화한다" 가 아니다.**
  경로 오타·권한·시간 초과로 조용히 죽을 수 있다. 발화 확인은 `verify` 다

### 검증 규율 — 통과는 근거가 아니다

게이트를 만들거나 고치면 **막으려는 상황을 실제로 만들어 놓고** 막히는지 본다.
게이트가 아무 일도 안 해도 통과는 나오기 때문이다.

그리고 **변조를 빼면 다시 통과하는지도** 본다. 한쪽만 보면
"항상 막는 훅" 과 구별되지 않는다.

`verify` 는 검사마다 **막힘 사례와 통과 사례가 둘 다 있는지**를 스스로 확인하고,
한쪽이 없으면 그 사실을 찍는다.

## 10. 구조

```
core/        판정만 한다. 네 값 중 하나를 돌려주고, 종료 코드를 모른다
adapters/    입력을 읽고 판정을 종료 코드로 옮긴다. 판정은 하지 않는다
  claude-code/   훅 입출력 · 전역 설치
  git/           pre-commit · commit-msg · 저장소별 설치
scripts/     사람이 돌리는 것 — 검증 · 생존 판정 · 예산 · 이식
template/    새 프로젝트에 놓을 문서 골격
skills/      그 골격을 채우는 절차 (온보딩 · 회고)
decisions/   왜 그렇게 정했나
```

경계는 하나다 — **판정은 `core/` 에만 쓴다.**

## 11. 여기에 없는 것

**결정의 *내용*.** 형식만 준다.

남의 결론을 규칙으로 물려받는 것은 **외부 배포판을 검토 없이 받는 것**과 같다.
남의 프로젝트는 남의 제약 아래에서 그 답에 도달했고, **그 제약이 여기에도
있는지는 별개의 판단**이다.

그래서 이 하네스는 "이렇게 정해라" 를 주지 않고,
**"정했으면 근거와 뒤집힐 조건을 적어라" 를 준다.**

그 밖에 하지 않는 것 —

- CI · 원격 서버 · 대시보드 (로컬 저장소 안에서 끝난다)
- 학습한 것을 자동으로 규칙으로 승격하기 (관측은 사람이 읽고, 승격은 손으로)
- 특정 도메인의 코딩 규칙 (그건 대상 프로젝트의 몫이다)
- `git push` (원격은 사람이 한다)
